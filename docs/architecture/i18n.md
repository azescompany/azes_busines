# Internationalization (i18n)

`packages/i18n` centralizes translation infrastructure for web, Next.js, and React Native.

## Structure

- Translation keys: namespaced, dot-notation (e.g. `common:auth.sessionOtherDevice`).
- Locale structure: one directory per locale, one JSON per namespace.
- Default / fallback locale: `az`. Supported platform locales: `az`, `en`, `ru`.
- Shared package namespaces stay minimal (`common`). Product copy lives in each app
  (e.g. admin `general.json`, account `account.json`) and is merged via
  `createI18nInstance({ appId, resources })`.
- Locale preference is **per app**: `azes.i18n.locale.<appId>` (never a shared global key across products).
- Lazy loading: namespaces/locales loaded on demand to keep bundles small.
- Formatting: dates, numbers, currency via the platform Intl APIs behind helpers.
- Pluralization: i18next plural rules.
- Language UI: `@azes/ui-web/locale` (`AzesLocaleMenu` with flag marks; `AzesAccountMenu` for
  fixed-width account actions).

## Platform integration

- Web/Next.js: i18next + react-i18next; Next.js server/client rendering respected.
- React Native: i18next with a device-locale detector; async storage for chosen locale.

## Rules

- Avoid app-specific translation implementations unless genuinely necessary; apps provide their
  own namespaces but reuse the shared setup.
- Keys are the source of truth; never hardcode user-facing strings in components.
